# Content Registry™

The single source of truth for what content exists, whether it's approved, and when it goes live. Part of the **Content Publishing Engine™** (`scripts/content-publishing/`) — the state-driven replacement for the old PR-merge-based scheduler. See `governance/CONTENT_PUBLISHING_ROOT_CAUSE_REPORT.md` for why that replacement happened.

## What lives here

```
content-registry/
  articles/
    <slug>.json     — one file per article, never a shared array
  history.jsonl      — append-only Publication History, one JSON line per publish attempt
```

**One file per article is the load-bearing design choice.** A single monolithic `registry.json` array would reintroduce exactly the append-conflict risk this system exists to eliminate — two content PRs both adding an entry would race to edit the same file. One file per article makes every new article a uniquely-named new file, structurally conflict-free, the same way an article's own HTML file already is.

## Registry entry schema

```json
{
  "slug": "music-industry-runs-on-data",
  "title": "The Music Industry Runs on Data—Not Just Songs",
  "type": "blog",
  "category": "Metadata",
  "excerpt": "...",
  "author": "Royaltē Editorial",
  "readTime": "5 min read",
  "contentPath": "public/blog/music-industry-runs-on-data.html",
  "heroImagePath": null,
  "approvalStatus": "approved",
  "publishStatus": "published",
  "publishDate": "2026-07-24",
  "publishedAt": "2026-07-24T13:05:11Z",
  "articleVersion": 1,
  "createdAt": "2026-07-20T00:00:00Z",
  "lastModified": "2026-07-24T13:05:11Z",
  "sourcePr": 401
}
```

`approvalStatus` (`pending`/`approved`) and `publishStatus` (`draft`/`scheduled`/`published`/`archived`) are separate fields — Board sign-off and lifecycle state are different concerns. An article is eligible to publish when `approvalStatus === 'approved' && publishStatus === 'scheduled' && publishDate <= today`. See `scripts/content-publishing/schema.mjs` for the authoritative validation logic.

## How to add a new article

1. Write the article (`public/blog/<slug>.html` or `public/education/<slug>.html`), duplicate from `_template.html` as before. This still merges via a **normal, human-reviewed PR** — nothing about content review changed.
2. Add `content-registry/articles/<slug>.json` (same PR, or a follow-up — either is fine, they're independent files). Set `approvalStatus: "pending"`, `publishStatus: "draft"` until the Board approves it.
3. Once the Board approves a publish date, set `approvalStatus: "approved"`, `publishStatus: "scheduled"`, `publishDate: "YYYY-MM-DD"`.
4. That's it. The next scheduled run (Tuesday/Thursday, 9am ET) picks it up automatically once its date arrives — no merge, no label, no PR-body scheduling block. `.github/workflows/content-validation.yml` (Workflow A) lints the registry on every PR touching `content-registry/**`; `.github/workflows/scheduled-publish.yml` (Workflow B) is the only thing that ever flips `publishStatus` to `published`.

A `draft`/`pending` article never appears on any public page, not even as a "coming soon" teaser — only `approved` articles do (whether already `published` or still `scheduled`).

## Generated files — never hand-edit

These are fully regenerated on every publish run from the current registry state. Hand edits will be silently overwritten on the next run:

- `public/js/blog-posts.js`, `public/js/education-posts.js` — whole-file generated.
- `public/blog.html`, `public/education/index.html`, `public/sitemap.xml` — only the region between `<!-- CONTENT-PUBLISHING-ENGINE:<NAME>:START -->` / `:END` markers is generated; everything else (nav, hero, footer, non-article URLs) stays hand-authored and untouched.
- `public/rss.xml`, `public/search-index.json` — new, whole-file generated.

Static HTML generated by a script (not hand-typed) is not the same thing as client-side JS rendering — the long-standing "do not JS-render cards from blog-posts.js" rule (crawler/AI-search visibility) is about deferring rendering to the browser at runtime. A script producing static HTML at publish time is the same kind of artifact hand-authored cards always were.

## Publication History™

`content-registry/history.jsonl` is append-only — never edited, never deleted, one JSON object per line per publish attempt (success or failure), including "ran, nothing was due" runs. It's the durable, queryable audit trail; a future Mission Control card can read it directly. Query it with `loadHistory()` from `scripts/content-publishing/registry.mjs`, or `describeScoreHistoryEvent`-style tooling if that's ever built for content (not built yet — no current need).

## Recovery

An article whose `contentPath` doesn't exist yet when its `publishDate` arrives is skipped, not published, and logged as a `publish_failed` event — it stays `scheduled` and is retried automatically on the next run (or via manual `workflow_dispatch`) once its content PR merges. Nothing is ever lost.
